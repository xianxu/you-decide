# Review pipeline

Every artifact in the public substrate (and the skill bundle itself) must be generated by one agent and reviewed by another. Goal: catch fact errors, math errors, missing disambiguation (e.g., two candidates with same name), source-tier abuse, internal inconsistency.

## Two independence axes

1. **Fresh context** — the reviewer agent starts with no memory of how the artifact was produced. They re-derive judgments from the source citations + the substrate. Catches "the author talked themselves into something" failures.
2. **Different AI stack** — when feasible, the reviewer runs on a different model family / vendor than the author. Catches systematic failure modes specific to one stack. (Not always feasible; same-stack fresh-context review is still better than no review.)

## Per-file frontmatter contract

Every reviewable file declares state in its frontmatter so unreviewed work is **greppable**, not invisible-by-omission:

```yaml
---
generated-by: <stack used to generate, e.g. claude / gemini / gpt-4 / human>
generated-on: <YYYY-MM-DD>
review: <not-done | passed | failed | in-progress>
reviewed-by: <stack used to review>             # required when review != not-done
reviewed-on: <YYYY-MM-DD>                        # required when review != not-done
review-ref: data/reviews/<year>/<date>-<batch>.md     # link to the session output
---
```

**`review: not-done` is mandatory on fresh files** — silent omission is the anti-pattern this contract guards against.

## Audit

`scripts/audit-review.sh` greps the substrate for:
- Files with `review: not-done`
- Files whose `generated-by` and `reviewed-by` are the same stack (independence failure)
- Files missing the `review:` field entirely (contract violation)

Run before committing shared substrate; surface unreviewed work for batched review.

## review.md (the sub-skill)

`you-decide/review.md` is the skill that performs review. It accepts parameters for breadth:

- A single file path → review that file
- A directory → review all files under it
- A batch label → review all files in the named batch (e.g., a per-city run)

Output goes to `data/reviews/<year>/<date>-<batch>.md` — captures findings, source-tier verifications, math re-derivations, disambiguation checks. Each reviewed file's frontmatter is updated with `review:`, `reviewed-by:`, `reviewed-on:`, `review-ref:`.

## Review gate

Mandatory before any commit to shared `data/candidates/`, `data/elections/`, `data/controversies/` directories. The skill dispatches review before letting the user commit. Reads (`who-to-vote-for/.../<slug>-read.md`) are user-private but benefit from the same mechanism — primary value is catching arithmetic errors in the weighted-total math (the scoring contract in [algorithm](algorithm.md#scoring-contract) gives review a sharp invariant to check).

## What review does NOT do

- It does not regenerate substrate. Findings are filed; fixes are the original-author's responsibility (or a follow-up generation pass)
- It does not run on every commit (would defeat cache-first). Review batches are sized to fit the reviewer's fresh-context budget
